System Architecture

How NexusQuery works

A natural language question travels through five layers before returning as a narrated answer — Claude generates SQL, DuckDB executes it directly against Gold Delta tables in ADLS Gen2, and Claude narrates the result. No Databricks cluster required at query time.

Seven steps from English question to narrated answer · DuckDB reads Gold Delta files directly · no Databricks cluster at query time

Key design decisions

DuckDB replaces Databricks at query time
DuckDB runs inside the Flask process. No cluster cold-start, no DBU charges, no HTTPS round-trip to Databricks. Gold Delta files are read directly from ADLS Gen2 via the azure extension. First query ~1–2s. Subsequent queries ~50–200ms.
Two Claude calls per question
Call 1: schema context + question → SQL. Call 2: SQL + query results → plain English narration. Claude never sees raw data directly — only the result set.
SQL safety guard
is_safe_sql() inspects every Claude-generated query before DuckDB executes it. DROP, DELETE, INSERT, UPDATE, and all DDL are blocked regardless of how the question is phrased.
Databricks only for the pipeline
poc-cluster runs Bronze → Silver → Gold notebooks on demand, then terminates. The chatbot never needs it. Monthly demo cost: ~$1.

Layer by layer

What happens at each step

Each layer has one responsibility. The layered design means swapping DuckDB for Trino, or Claude for another LLM, requires changing exactly one file.

STEP 01 — USER LAYER
Browser → Flask
The user types a natural language procurement question into the Bootstrap 5 chat interface. JavaScript sends a POST request to /chat/message with the question and full conversation history. Flask session maintains multi-turn context.
Flask 3.1 Bootstrap 5 dark Jinja2 gunicorn
STEP 02 — APP LAYER
ChatService + schema injection
ChatService.process_turn() orchestrates the full request. It loads schema_context.py which injects all six Gold table schemas and ten SQL rules into the system prompt. Rules include: no catalog prefix, budget join key normalization, OTD region join pattern, and fact table constraints.
ChatService schema_context.py 6 Gold schemas 10 SQL rules
STEP 03 & 06 — INTELLIGENCE LAYER
Anthropic Claude — two calls
Call 1 — SQL generation: Claude receives the enriched system prompt + user question. It returns a single ```sql block, nothing else.

Call 2 — Narration: After DuckDB returns results, Claude receives the SQL + result rows and narrates the findings in plain English with business context.
claude-sonnet-4 api.anthropic.com NL → SQL results → narration
STEP 04 — QUERY ENGINE
DuckDB — embedded in Flask process
DuckDB is not a separate server. It runs inside the gunicorn worker process. On startup it installs the delta and azure extensions, authenticates to ADLS Gen2 using the storage account key, and registers six delta_scan() views — one per Gold fact table.

At query time: reads the Delta transaction log, applies predicate and projection pushdown, streams only the needed Parquet columns from ADLS Gen2, and returns rows in milliseconds.
DuckDB delta extension azure extension in-process no cluster
STEP 05 — STORAGE LAYER
ADLS Gen2 — Gold Delta tables
Six Gold fact tables live in the gold/ container of the ADLS Gen2 storage account as Delta Lake files (Parquet + transaction log). They were written by the Databricks Gold notebook using abfss:// protocol and are read by DuckDB via the same protocol.

Data range: January 2024 – June 2024. Tables: spend by supplier, spend by category, OTD by supplier, invoice match, budget variance, defect rate.
ADLS Gen2 Delta Lake Parquet abfss:// HNS enabled
STEP 07 — PIPELINE LAYER (offline)
Azure Databricks — Bronze → Silver → Gold
The poc-cluster (Standard_DS3_v2, Runtime 15.4 LTS) runs three notebooks to populate the Gold tables from raw CSV files. It is not used by the chatbot. It is started manually when new data needs to be processed, and terminated immediately after the Gold notebook completes.

Cost: ~$0.61/hour while running. Zero when terminated.
Azure Databricks Premium Spark 3.5 Unity Catalog offline only

Data Model

Six Gold fact tables

Pre-computed KPI aggregates. DuckDB registers each as a view via delta_scan() at startup. Claude queries them by plain name — no catalog or schema prefix needed.

fact_spend_by_supplier
Monthly spend per supplier with tier and region breakdown.
supplier_id tier region _month_key total_spend
fact_spend_by_category
Monthly spend per category with parent category and spend band.
category_name parent_category spend_band total_spend
fact_otd_by_supplier
On-time delivery % per supplier per month. Join to spend table for region.
supplier_name tier total_deliveries otd_pct
fact_invoice_match
Invoice match rate — % of invoices within 1% of PO value — and average variance.
invoice_count match_rate_pct avg_variance_pct
fact_budget_variance
Budget vs actual spend by plant and category. No supplier_id — join on plant_id and category_id only.
plant_id variance_pct status month_join_key
fact_defect_rate
Defect events and defect rate % per supplier per month. Lower is better.
defect_events total_defect_qty defect_rate_pct
